## Email service — live probe results (2026-10)

The origin's API is alive and answers server-side (CORS blocks the browser, curl does not):

| Probe | Result |
|---|---|
| `GET /api/pricing/landing?tz=Asia/Calcutta` | **200** · `regionCode IN` · `planType letter` · `priceAmount 36900` (₹369.00) |
| `POST /api/password-reset/request` `{email}` | **400** `{"code":"bad_request","field":"request","reason":"invalid_json"}` |
| `POST /api/gifts/find-by-email` `{email}` | **403** `{"error":"Verificação de segurança inválida"}` |

Reading:
- The reset endpoint rejects the bare `{email}` body — it almost certainly needs a Turnstile/CSRF
  token alongside the address, which is why any hand-rolled probe reads as `invalid_json`.
- `find-by-email` explicitly returns **"invalid security verification"**, i.e. bot protection.
- **Delivery itself cannot be verified from outside.** The only honest test is to request a reset
  for a mailbox you own and watch for the mail.

**Live price discrepancy (important for rebranding):** the pricing API currently returns
`priceAmount: 36900` for the letter plan (₹369.00), while the captured landing page showed
**₹199.00** for the Birthday Letter and **₹299.00** for the Party. Prices have moved since the
capture (or are A/B/region dependent). Our replica shows the captured values on purpose; when
rebranding, read the live API rather than trusting the snapshot.

**In the replica:** there is no email service, and none is needed — the product delivers a link
and a QR code that the buyer sends. The only local services running are the AI bridge
(`127.0.0.1:8787`) and the FreeLLMAPI gateway (`127.0.0.1:31415`).
